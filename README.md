# Heretous

Чатрулетка для групповых видеозвонков.

HTTP-сервер с YAML-конфигурацией, PostgreSQL, SQL-миграциями, структурированными логами и корректным завершением. Бизнес-логика пока не реализована.

## Идея

Сервис объединяет людей, которые хотят вместе выпить и пообщаться. Пользователь выбирает свой напиток и присоединяется к столу или создаёт новый. У каждого стола есть ограничение числа участников, свои правила и ограничения.

Планируется автоматическое создание аккаунта с хранением информации об аккаунте в `localStorage` браузера. Пользователь сможет задать логин и пароль, чтобы сохранить доступ.

## Требования и запуск

Для запуска всего продукта нужен Docker Engine с Compose v2. Go и PostgreSQL на компьютере не требуются. Команды выполняются из корня репозитория.

Приложение использует заранее подготовленный локальный образ `heretous:local`. Автоматическая сборка отключена; если образа нет, запуск завершится ошибкой. Сервисы `tests` и `deps` используют готовый `golang:1.25-bookworm`.

```sh
docker compose up --wait --wait-timeout 120
```

Compose запускает PostgreSQL 18 и приложение, которое применяет миграции перед запуском HTTP. Compose ждёт готовности приложения. Данные приложения сохраняются в томе `postgres-data`. HTTP и PostgreSQL доступны с этого компьютера на портах 8080 и 5432.

```sh
curl http://localhost:8080/healthz
curl http://localhost:8080/readyz
```

Ответ: HTTP 200, `{"status":"ok"}`. `/healthz` проверяет HTTP-процесс; `/readyz` проверяет соединение с PostgreSQL и возвращает 503 при недоступной базе. Неизвестные пути возвращают 404, неподдерживаемые методы — 405.

Для остановки окружения выполните `docker compose stop`.

## Конфигурация

Настройки читаются из [`config.yaml`](config.yaml) при запуске; в Compose файл монтируется только для чтения. Неизвестные ключи и некорректные значения останавливают запуск. Приоритет: значения по умолчанию → YAML → непустые переменные окружения. Само приложение `.env` не загружает; Compose использует его для подстановок.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `CONFIG_PATH` | `config.yaml` | Путь к обязательному YAML-файлу, относительно рабочего каталога |
| `HTTP_ADDR` | `:8080` | Адрес и порт HTTP-сервера; `127.0.0.1:8080` для доступа только с этого компьютера |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s` | Положительное время ожидания текущих запросов при завершении |
| `LOG_LEVEL` | `INFO` | Уровень логирования: `DEBUG`, `INFO`, `WARN`, `ERROR` |
| `DATABASE_URL` | Значение `database.url` в YAML | Строка подключения PostgreSQL |

В YAML также заданы `migration_timeout`, таймаут подключения, лимиты пула и срок жизни соединения. Перед запуском HTTP приложение проверяет подключение к БД и применяет миграции под блокировкой PostgreSQL. `migration_timeout` ограничивает ожидание блокировки и выполнение миграций; ошибка или истечение таймаута завершает процесс с кодом 1. При завершении приложение закрывает пул после остановки HTTP.

Compose использует `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` (по умолчанию `heretous`) для создания базы и формирования `DATABASE_URL` сервиса `app`. Это настройки локальной разработки; специальные символы в учётных данных должны быть совместимы с URI. Изменение этих переменных не меняет пользователя и пароль в уже созданном томе PostgreSQL.

При локальном запуске с установленным Go 1.25+ сначала запустите PostgreSQL, затем сервер. Миграции он применит автоматически. Пример для PowerShell:

```powershell
$env:HTTP_ADDR = '127.0.0.1:8081'
$env:LOG_LEVEL = 'DEBUG'
go run ./cmd/server
```

Логи пишутся в stdout в формате JSON. Для HTTP настроены таймауты: чтение заголовков — 5 секунд, чтение запроса — 10 секунд, запись ответа — 15 секунд, простой соединения — 60 секунд.

## Сборка и остановка

```sh
go build -o bin/server ./cmd/server
```

На Windows:

```powershell
go build -o bin/server.exe ./cmd/server
.\bin\server.exe
```

`Ctrl+C` или `SIGTERM` запускает завершение: сервер перестаёт принимать соединения и ждёт текущие запросы до `HTTP_SHUTDOWN_TIMEOUT`. После истечения срока соединения закрываются принудительно. Штатное завершение возвращает код 0; ошибка конфигурации, запуска или завершения — код 1. Для работы с сигналами запускайте собранный бинарный файл напрямую: поведение передачи сигналов через `go run` зависит от платформы.

## Структура

```text
cmd/server/       точка входа, логирование, обработка сигналов
internal/config/  чтение и проверка конфигурации
internal/app/     запуск и завершение HTTP-сервера
internal/database/ подключение к PostgreSQL и настройка пула
internal/httpapi/ маршруты и HTTP-обработчики
migrations/       SQL-миграции, встроенные в бинарный файл
tests/system/     HTTP-проверки работающего продукта
```

## Проверки

Зависимости загружаются через Compose. Сервис `deps` форматирует Go-файлы и обновляет `go.mod`/`go.sum`; используйте его при изменении зависимостей:

```sh
docker compose -f docker-compose.yml --profile tools up --exit-code-from deps deps
```

Затем поднимите весь продукт и запускайте проверки на работающем окружении:

```sh
docker compose -f docker-compose.yml up --wait --wait-timeout 120
docker compose -f docker-compose.yml run --rm -T tests
```

Сервис `tests` имеет метку `com.heretous.task=test` и профиль `test`, поэтому обычный `docker compose up` его не запускает. Команда выполняет `go vet` и все тесты с детектором гонок, без кэша результатов и с ограничением 60 секунд на пакет. Текущие исходники монтируются только для чтения; отдельный образ тестов не нужен. Кэши сборки и модулей сохраняются в именованных томах. При изменении приложения требуется отдельно обновить `heretous:local`, чтобы системные тесты проверяли актуальный сервер. Агентам запрещено запускать сборку, в том числе косвенную компиляцию при тестировании, согласно `AGENTS.md`.

Перед тестами Compose ждёт готовности приложения и отдельного PostgreSQL `postgres-test`. Тестовая БД хранится в памяти, не публикует порт и не использует данные приложения. Интеграционные тесты создают и удаляют собственные базы. Системные тесты обращаются к запущенному приложению через `TEST_APP_URL`. Окружение остаётся запущенным после проверок.

Запуск отдельной группы тестов:

```sh
docker compose -f docker-compose.yml run --rm -T tests go test -race -count=1 -timeout=60s -run TestShutdown ./internal/app
```

Скилл для этого процесса находится в [`.agents/skills/heretous-tests/SKILL.md`](.agents/skills/heretous-tests/SKILL.md); имя для вызова — `$heretous-tests`.

При запуске Go-тестов вне этого процесса интеграционные проверки пропускаются, если не заданы `TEST_DATABASE_URL` и `TEST_APP_URL`. Такой прогон не заменяет полную проверку продукта через Compose.

## Миграции

Миграции выполняются через библиотеку [Goose](https://pressly.github.io/goose/documentation/provider/) при каждом старте сервера, до открытия HTTP-порта. SQL встроен в бинарный файл `server`. Применённые версии хранятся в `goose_db_version`; уже выполненные миграции повторно не применяются. Все инстансы используют общий session advisory lock PostgreSQL: один выполняет миграции, остальные ждут освобождения блокировки, затем проверяют и применяют оставшиеся изменения. По умолчанию каждая SQL-миграция транзакционная. Для запуска приложения отдельный шаг миграций в CI/CD не требуется.

Первая миграция создаёт схему `app`, без предметных таблиц. Добавляйте файлы `migrations/00002_description.sql` и далее с секциями `-- +goose Up` / `-- +goose Down`; для применения новых файлов пересоберите образ. Уже применённые миграции не изменяйте. `migration_timeout` ограничивает ожидание блокировки и выполнение миграций при старте сервера. Тесты отката выполняются исключительно на `postgres-test`.

При обновлении нескольких инстансов миграции должны оставаться совместимыми с ещё работающей предыдущей версией приложения. Блокировка сериализует миграции, но не останавливает обработку запросов уже запущенными инстансами. Учётной записи приложения нужны права на изменения структуры БД.

## Образ Docker

`Dockerfile` содержит два этапа: `build` (компиляция сервера) и `runtime` (Debian Bookworm Slim с приложением, `curl` и корневыми сертификатами). Финальный образ работает от непривилегированного пользователя. Compose задаёт `HTTP_ADDR=:8080`, проверяет `/readyz` через `curl`, публикует порты только на `127.0.0.1` и даёт приложению 15 секунд для завершения, при внутреннем таймауте 10 секунд. При изменении таймаута в YAML согласуйте `stop_grace_period` в Compose.

Период `healthcheck.start_period` приложения равен 65 секундам с учётом стандартного `migration_timeout: 1m` и подключения к БД. При увеличении времени миграций согласуйте этот период и `--wait-timeout`. Фиксированный опубликованный порт предназначен для одного локального инстанса; для нескольких инстансов нужны отдельные порты или балансировщик.
